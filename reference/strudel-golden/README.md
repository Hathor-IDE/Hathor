# Strudel Golden Fixtures

Ground-truth event fixtures for the Strudel pattern engine, generated by
**executing Strudel's real `queryArc` function** (not by hand). These fixtures
are intended as golden ground-truth for differential testing of a from-scratch
C++ port of the Strudel pattern engine.

- **Engine used:** `@strudel/core` and `@strudel/mini` (installed via the repo's
  pnpm workspace, so the *actual current implementation* in `packages/core` and
  `packages/mini` is imported — not a stale npm-published version).
- **Query mechanism:** `Pattern.queryArc(begin, end)` returns the array of
  `Hap` events active over the time span `[begin, end)` (in cycles).
- **Mini-notation parsing:** every mini-notation string is parsed through
  Strudel's real mini-notation parser via `m(str)` from `@strudel/mini`
  (which uses the `krill-parser.js` PEG grammar). Direct-API fixtures use
  `core.*` combinators (`stack`, `rev`, `every`, `iter`, `degradeBy`, `fast`,
  `slow`).
- **Provenance recorded per fixture:** `strudel_version_or_commit` field.
- **No hand-written values:** every number in every fixture came from an
  actual call into Strudel's real query function. If a pattern threw an error,
  the error is recorded in the fixture rather than the event list being omitted.

## Regenerating all fixtures

From the repository root (after `pnpm install`):

```sh
node scripts/generate-golden-fixtures.mjs
```

This writes/overwrites all `*.json` files in `reference/strudel-golden/`
(including `README.md` is NOT overwritten by the script — this file is hand-written).

Regenerate whenever the Strudel source changes (e.g. after pulling new commits
or running `pnpm install` against a newer version) so the C++ port is verified
against the current implementation.

## Fixed query arc set

Every "standard" fixture is queried over these 6 arcs (expressed as exact
fractions), for every pattern:

| # | arc `[start, end)` | label |
|---|--------------------|-------|
| 1 | `[0, 1)`           | one cycle |
| 2 | `[0, 0.25)`        | first quarter of cycle 0 |
| 3 | `[0.25, 0.5)`      | second quarter of cycle 0 |
| 4 | `[0.5, 0.75)`      | third quarter of cycle 0 |
| 5 | `[0.75, 1)`        | fourth quarter of cycle 0 |
| 6 | `[0, 2)`           | two cycles |

Some fixtures additionally query an extra arc (see notes in each fixture's
`description` and `arcs_used` field). The full list of arcs actually queried
for each fixture is recorded in the top-level `arcs_used` field of that file.

## Output format

Each `*.json` file has the shape:

```json
{
  "description": "human-readable description of the pattern and what it's testing",
  "mini_notation": "the exact mini-notation string, or null if constructed via direct API",
  "strudel_version_or_commit": "1.2.6",
  "arcs_used": [ [[startNum, startDen], [endNum, endDen]], ... ],
  "precision_note": "Time values are serialized as ...",
  "queries": [
    {
      "arc": [[0,1],[1,1]],
      "events": [
        { "whole": [[0,1],[1,4]], "active": [[0,1],[1,4]], "value": "bd" }
      ],
      "error": null
    }
  ]
}
```

- `whole` and `active` are each `[ [startNum, startDen], [endNum, endDen] ]`
  — exact rational cycles serialized as `[numerator, denominator]` integer pairs.
- `error` is `null` on success; if a query threw, it is `{ "message": ..., "name": ... }`.
- `arcs_used` lists every arc (as exact pairs) that was queried, in order. The
  `queries` array corresponds 1:1 with `arcs_used`.

## Number representation / precision

Strudel's core engine uses `fraction.js` internally (patched in
`packages/core/fraction.mjs`), so all internal time values are **exact
rationals**. We serialize them as `[numerator, denominator]` integer pairs
(e.g. `[1, 4]` for `0.25`, `[1, 3]` for `1/3`, `[7, 16]` for `0.4375`). The
`precision_note` field documents this. If a value cannot be represented as an
exact fraction from Strudel's internal representation, the script falls back to
attempting conversion via `Fraction(v)`; consumers may compare with a tolerance
for any such non-exact cases, though in practice all time values here are exact.

### euclid
| file | mini_notation | what it covers |
|------|---------------|----------------|

| `euclid-7-16-2.json` | `"bd(7,16,2)"` | k=7, n=16, offset=2 form (Samba necklace). |

### degradeBy (correlation + edge cases)
| file | mini_notation | what it covers |
|------|---------------|----------------|
| `degrade-by-0.5-instance-a.json` | null | `core.degradeBy(0.5, m("bd*16"))` instance A, over `[0, 4)`. |
| `degrade-by-0.5-instance-b.json` | null | `core.degradeBy(0.5, m("bd*16"))` instance B, over `[0, 4)`. |
| `degrade-by-0.0.json` | null | `core.degradeBy(0.0, m("bd*8"))` — edge case 0% removal (all survive). |
| `degrade-by-1.0.json` | null | `core.degradeBy(1.0, m("bd*8"))` — edge case 100% removal (empty). |

**Correlation note for `degrade-by-0.5-instance-a/b`:** Strudel's `rand` signal is
deterministic on `(time, controls.randSeed)`, and `randSeed` defaults to `0`.
Consequently two independently-constructed `degradeBy(0.5, ...)` instances with
no explicit `.seed()` produce **identical** results — the two instances ARE
correlated. In the generated fixtures, `instance-a` and `instance-b` are byte-for-byte
equal event lists. This behavior is captured faithfully; a C++ port should
reproduce this identical correlation unless it intentionally introduces
per-instance randomness.

## Mini-notation syntax notes / corrections

All mini-notation strings below match Strudel's **current** syntax as of the
recorded version and were verified by successful parsing through `m(str)`. No
corrections were needed:

- Stack: comma syntax `"bd, sn"` is current (not `"bd sn"` which is fastcat).
- Fastcat: space-separated `"bd sn hh cp"`.
- Slowcat: angle brackets `"<bd sn hh>"`.
- Fast: `factor` multiplier with `*`, e.g. `"bd*4"`, `"[bd sn]*2"`.
- Slow: divisor with `/`, e.g. `"bd/2"`, `"[bd sn]/2"`.
- Euclid: `"bd(k,n)"` and `"bd(k,n,offset)"`.
- Replicate: `"bd!3 sn"`.
- Rest: `"~"`.
- Nested subsequences: `[sn hh]` (sequence group) and `<sn hh>` (polymeter group).
